智能客服售后工单分析

原始数据：`service_tickets.csv`；脚本：`analysis.py`；输出图：`analysis_result.png`

### 看到了什么（数据事实）

1. 总工单 1326 条，排除状态未回传的 51 条，有效工单 1275 条，成功闭环 1126 条，答错投诉 149 条，整体投诉率 11.69%。全部投诉造成人工损失 `149 × 120 = 17880分钟`。
2. 规则深度（rule_version_depth）和投诉风险存在关联：
   - 0-10 简易规则：工单 465 条，投诉 61 条，投诉率 13.12%，平均对话轮次 51.87
   - 11-20 中等规则：工单 394 条，投诉 38 条，投诉率 9.64%，平均对话轮次 53.29
   - 21-30 复杂规则：工单 416 条，投诉 50 条，投诉率 12.02%，平均对话轮次 53.40
3. 大区差异：华南客服部投诉率最高 16.01%；西南客服部最低仅 6.06%。
4. 类目差异：服饰鞋包投诉率最高 18.18%，其次生鲜食品 16.18%；家用电器投诉最低 5.75%。
5. 时序问题：存在工单用户咨询时间早于知识库规则同步时间，属于时序异常，该类工单更容易出现答复错误。

### 根问题

> 核心根因：部分高复杂度售后场景、高风险商品类目下，智能客服知识库答复稳定性不足，容易答错引发客诉；同时系统存在时序漏洞，在规则同步完成前就承接咨询，使用过期规则回答用户，放大出错风险。次要因素：不同大区业务工单结构差异，带来投诉率分化。

## 做了什么

1. 数据清洗：过滤 resolved_status 空值（未回传状态），筛选有效 1275 条样本；转换时间字段，计算用户咨询与规则同步的时间差。
2. 多维度分组统计：按规则深度、客服大区、商品类目、规则同步时差分组，统计投诉率与平均对话轮次。
3. 可视化：绘制多子图对比各维度投诉率，输出图片`analysis_result.png`。
4. 业务成本测算：模拟对 21-30 复杂规则工单提前人工审核，对比原有客诉损失和人工审核成本，评估方案净收益。

## 怎么证明有用

### 复现步骤

1. 克隆仓库，下载 `service_tickets.csv`、`analysis.py`、`requirements.txt` 放在同一目录。
2. 安装依赖：`pip install -r requirements.txt`
3. 执行脚本：`python analysis.py`
4. 控制台输出全部统计指标，自动生成分析图片`analysis_result.png`。

### 关键计算数字

1. 有效工单总数：1275，投诉工单：149，整体投诉率：11.69%，总投诉损失：**17880 分钟**
2. 规则深度分组指标：
   - 0-10 简易规则：投诉率 13.12%
   - 11-20 中等规则：投诉率 9.64%
   - 21-30 复杂规则：投诉率 12.02%
3. 大区投诉率：华南 16.01%，华北 14.37%，华东 10.49%，西南 6.06%
4. 类目最高投诉：服饰鞋包 18.18%，生鲜食品 16.18%
5. 模拟收益（21-30 复杂规则工单全部提前转人工审核）：
   - 复杂规则工单总数：416，其中投诉：50
   - 原损失：`50 * 120 = 6000`分钟；全部提前转人工审核成本：`416 *12 = 4992`分钟
   - 净节约时间：**1008 分钟**，方案具备正向收益。

> 说明：业务收益模拟为推演测算，非真实线上结果。

### 业务建议

1. 不直接一刀切全量拦截：针对 21 及以上深度工单，结合商品类目、对话轮次做多维度风险打分，只拦截高风险子集，避免人工负载过载。
2. 修复系统时序 bug：禁止规则全量同步完成前承接咨询，杜绝使用过期知识库作答。
3. 专项优化高投诉类目（服饰鞋包、生鲜食品）的售后知识库，简化复杂逻辑，降低规则深度。
4. 灰度试点上线：小流量试运行拦截策略，持续监控投诉率、人工工单负载两个指标，动态调整阈值。
